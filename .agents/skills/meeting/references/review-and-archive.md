# 会后理解、复盘与归档

## 讲懂会议

“帮我理解／都讲啥”优先给一条主线，再用具体例子串起：遇到的问题 → 方法在做什么 → 输出有什么用途 → 怎样判断可信。

少量术语解释嵌入对应位置。先检查用户是否把材料当模型、把模型架构当软件、把预测误差当材料真实性、把能量高低当唯一性能指标。温和指出具体混淆，不把“先学所有专业课”设为入门前提。

解释是对纪要的教学补充，不能回写成会上讲者实际说过的内容。用户只有局部疑问时只解答局部，不自动重做整场纪要。

## 个人学习复盘

按用户需要选择：
- 本次理解了什么：用用户能解释清楚的语言概括。
- 与已有知识怎样相通：例如图片到类别、结构到能量与力、问题参数到解场。
- 还没弄懂什么：一两项关键障碍，不铺满课程清单。
- 下一步：给一个可执行的小任务和掌握标准，例如能说明某张图的输入、标签、误差和适用条件。

这些是学习建议，不属于会议布置的待办。用户没有实际运行、计算或完成验证时，不代其写成“我已经掌握／证明／实现”。

## 给老师的简短总结

只起草文本，未经明确授权不发送。通常一段即可：一个具体收获、一个方法理解、一个仍需学习或验证的点。避免用模型名堆砌收获，避免过度自责、替用户认领团队成果。

需要时给更朴素的版本，例如“我理解了模型输入什么、学习什么，以及为什么要验证”，不夸大专业熟练度。

## 多会议整理

1. 先列出实际可访问的会议资料，写明日期依据、主题、类型及是预习还是会后记录。
2. 仅按用户范围筛选。一次会议的多个片段不算多场，同日不同主题不合并；不把讲座自动称作组会。
3. 按日期和主题建立时间线，比较研究问题、方法、已报告进展和明确任务。
4. 只有后续来源明确表明完成或替代，才能更新状态；未再提到不等于已完成，建议反复出现不等于反复决定。
5. 区分正常方案演进与仍未解决的矛盾，并给两侧来源。跨会串联的学习启发标为助手总结。

可用表头：日期及依据｜主题｜类型／阶段｜主要进展｜未决问题｜来源。缺失日期保留待核实，不按文件修改时间伪造时间线。

## 文件保存

用户说“生成TXT放到会议文件夹”，先寻找明确指定位置或当前工作流已经确认的“组会 学术会议纪要”目录。找不到且位置影响交付时问路径；也可先生成聊天内容。不要把某台设备的绝对路径写成跨设备默认。

建议文件名：
- `2026年10月24日 智能计算力学 学术报告纪要.txt`
- `2026年10月24日 铁电材料 课题组组会纪要.txt`
- `2026年10月21日 数据高效微调 研讨会预习.txt`
- `日期待核实 缺陷结构 学术报告纪要.txt`

日期与主题只是命名示例，不是预设历史事实。只有用户明确授权按整理日期归档时，日期不明的文件可用整理日期，正文标明“归档日期，非已确认会议日期”。

TXT用UTF-8，正文保留编号、来源范围、日期依据、必要问答和待核对事项。表格过宽时改成逐项列示，避免依赖Markdown渲染才能读懂。

保存前检查现有文件：
- 原始转写、录屏或自动纪要只作来源，不覆盖。
- 用户明确要修订现有纪要时，回读当前版本后定点更新，保留有用内容。
- 同名来源内容变了，要将旧记录和新材料的依据分开，不能声称旧全文仍存在。
- 保存新纪要时，用日期、主题或版本后缀区分，避免覆盖另一场会议。

写入后回读内容，确认真实路径、编码、标题、覆盖范围和文件结尾，最后给出可点击文件链接。根据材料规模选择适度抽查，不声称文件存在即可证明科学结论正确。

生成会议索引只在用户要求汇总、已有索引需要同步或明确有助本次归档时进行；不要把每次小问题都变成多文件项目。

## 发布与权限

本地保存、发给老师、上传公共仓库是不同动作。仅在用户明确要求相应操作时执行。发布可复用skill时，例子使用抽象或虚构内容，不把私密会议原文、录屏、联系方式或私人评价一起上传。
