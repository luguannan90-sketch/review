# Workflow Retrospective

把“这次跑通了”转化为下一次可直接复用的工作方法。这个 Skill 只沉淀已经被验证的经验，不把猜测、偶然现象或未经确认的偏好写成硬规则。

## 何时触发

- 一个非平凡任务已经完成，并且方法可能在未来重复使用。
- 开始同类任务前，先检查并读取已有的相关 Skill。
- 任务失败但暴露出可复用的诊断线索时，可以记录失败模式；不要把失败方案当成推荐方案。

不要为一次性的小修改、纯问答或没有可验证结果的尝试创建新 Skill。

## 开始同类任务前

1. 根据任务对象、工具、文件类型和关键错误词搜索现有 Skill。
2. 读取最相关 Skill 的完整 `SKILL.md`；若它引用了特定 reference，只读取当前模式需要的部分。
3. 区分“必须遵守的约束”“已验证的推荐做法”和“待确认假设”。如果已有经验与当前任务冲突，以当前用户明确要求和当前证据为准。

## 任务完成后的沉淀流程

只有在结果已经通过适当验证后才进入沉淀：例如输出可打开、测试通过、关键数据核对一致，或用户明确确认成功。

按以下顺序提炼：

1. **目标与适用范围**：这套方法解决什么问题，不解决什么问题。
2. **前置条件**：所需输入、权限、工具、目录结构、版本或外部状态。
3. **执行步骤**：只记录影响决策或可靠性的步骤；注明关键分支及选择依据。
4. **判断标准**：如何知道每一步和最终结果是正确的，优先写可观察证据。
5. **坑点与失败原因**：记录实际遇到的错误、误区和触发条件；区分根因、症状和猜测。
6. **恢复与替代路径**：失败时先做哪些低风险检查，何时重试，何时停止并请求确认。
7. **复用入口**：未来遇到什么信号应加载该 Skill，以及需要用户补充哪些信息。

## 写作与维护标准

- Skill 名称使用小写连字符，描述要能准确区分适用任务。
- 保持 `SKILL.md` 自包含且简洁；只有确实需要按模式加载的长文档才放入 `references/`，并在入口文件中说明读取时机。
- 不复制通用常识，不写“永远”“一定”这类未经风险证明的绝对规则。
- 每条关键经验都尽量绑定证据：命令结果、测试、文件位置、用户确认或可复现现象。
- 新经验应先修正或补充现有 Skill，而不是为相近问题不断创建重复 Skill。
- 经验过时、与当前工具行为不符或被新证据推翻时，及时删除或改写，并保留必要的边界说明。

## 完成前检查

- 是否真的完成并验证了原任务？
- 读者能否仅凭 Skill 判断何时使用、如何执行、何时算成功？
- 是否明确标出了容易踩的坑、失败根因和停止条件？
- 是否把偶然细节误写成普遍规则，或遗漏了权限、版本、数据状态等前置条件？
- 运行 `quick_validate.py` 检查结构；若增加脚本，再单独执行脚本的关键路径。

沉淀完成后，在对用户的总结中简短说明：创建或更新了哪个 Skill、它记录了哪些经验证的内容，以及下次同类任务会先读取它。
