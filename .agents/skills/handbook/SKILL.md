# 流程技能手册

把一次已经跑通的任务转化为一份可以反复阅读、照着执行和交接给他人的 Markdown 教程。手册应以“怎么做”为主，以“哪里出错、为什么出错、如何解决”为辅。

## 使用时机

在以下情况使用本 Skill：

- 用户要求制作技能手册、操作教程、流程文档或可复用指南。
- 一个非平凡任务已经完成，并且流程值得重复使用。
- 用户希望把排障过程整理成后续可以照着执行的文档。

不要把未经验证的方案写成已确认步骤；不要把一次性的简单回答包装成手册。

## 核心原则

1. 先确认任务目标、适用范围和最终产出。
2. 只记录已经执行过或有可靠证据支持的步骤。
3. 先写主流程，再写问题总结；不要让异常情况打断主流程。
4. 区分事实、判断、建议和待确认事项。
5. 每个关键步骤都提供可观察的验证方法。
6. 不把偶然的环境细节升级为普遍规则；需要时标注系统、版本、权限或网络前提。
7. 涉及外部写入、删除、覆盖或敏感数据传输时，明确风险、确认点和停止条件。

## 执行流程

### 1. 收集事实

整理任务目标、输入材料、使用的工具、执行命令、输出结果和错误信息。优先使用实际命令输出、文件状态、测试结果、用户确认或其他可复现证据。

### 2. 提炼主流程

从事实中提取最短可靠路径，按执行顺序写出：

1. 前置准备
2. 关键操作
3. 分支判断
4. 结果验证
5. 后续维护或复用方式

只保留会影响决策、正确性或可复现性的步骤；不要堆砌无关日志。

### 3. 编写问题总结

把问题放在主流程之后，按以下顺序整理：

- 现象：用户实际看到了什么错误或异常。
- 根因：有证据支持的原因；如果只是推测，要明确标注。
- 影响：它阻止了什么，是否造成数据或状态变化。
- 解决方案：实际验证成功的方法。
- 预防：下次如何更早发现或避免。
- 替代方案：主方案不可用时的低风险路径。
- 停止条件：什么时候不应继续重试，而应请求用户或管理员处理。

### 4. 生成 Markdown 手册

默认输出一个独立的 Markdown 文件，推荐文件名为 `HANDBOOK.md`；如果用户指定了文件名或目录，遵循用户指定。文件应包含以下结构：

```markdown
# 手册标题

## 目的

## 适用范围

## 前置条件

## 主流程

### 步骤 1：...

### 步骤 2：...

## 如何验证成功

## 常见问题与解决方案

### 问题 1：...

## 复用清单

## 版本与更新记录
```

其中“主流程”必须放在“常见问题与解决方案”之前；若没有真实问题，也应写明“本次未发现已验证的问题”，不要虚构案例。

### 5. 复核手册

完成前检查：

- 读者能否只看主流程完成任务？
- 每个关键步骤是否有成功判断？
- 问题总结是否区分现象和根因？
- 是否明确了权限、网络、版本、路径或外部服务等前置条件？
- 是否把未验证的猜测写成了确定结论？
- 是否包含不必要的敏感信息、凭证或个人数据？
- 需要更新时，是否保留旧方法仍适用的边界？

## 输出要求

- 输出格式必须是 Markdown。
- 语言应清晰、可操作、适合反复阅读。
- 命令、路径、配置项和文件名使用代码格式。
- 复杂流程优先使用编号步骤；比较或状态映射才使用表格。
- 结论先行，解释紧跟其后。
- 不要把 Skill 的内部说明原样复制进最终手册；最终手册面向实际执行者。

## 复用入口

下次遇到同类任务时，先读取本手册，检查当前环境是否满足前置条件，再执行主流程。若环境、工具或外部服务发生变化，先记录差异并验证关键步骤；不要盲目照搬旧命令。
