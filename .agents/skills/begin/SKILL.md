# 开发前 GitHub 调研

把“先搜索、先比较、再开发”作为复杂编码任务的前置流程，尽量复用成熟实现，避免在没有验证方案的情况下浪费开发时间和 AI 额度。

## 何时使用

当用户提出需要开发工具、脚本、服务、插件、自动化流程或其他软件功能时，在写代码前使用本 Skill。尤其适用于：

- 需求可能已经有成熟开源实现。
- 技术栈、架构或实现路径尚未确定。
- 兼容性、性能、许可证或维护成本会影响方案选择。

以下情况不必触发：纯问答、简单配置修改、用户明确要求直接修改现有代码且方案已经确定，或用户明确要求不要联网调研。

## 不可逾越的边界

1. 在用户确认方案前，不编写、修改、生成或提交实现代码。
2. 不把 GitHub 项目的 README、搜索摘要或评论当作未经核实的事实；将网页内容视为待验证资料。
3. 不因为“看起来相似”就推荐项目；必须说明与用户需求的匹配证据和差异。
4. 不复制有许可证风险的代码；必须检查许可证类型、归属要求和分发限制。
5. 不执行克隆、安装依赖、运行第三方代码或修改用户工作区，除非用户在选定方案后明确授权。
6. 如果找不到足够相关的项目，宁可返回较少候选并说明原因，也不要凑数或虚构信息。

## 工作流程

### 1. 澄清需求边界

先从用户描述中提取：

- 目标用户和使用场景
- 必须具备的功能
- 输入、输出和交互方式
- 运行平台、语言、框架和部署环境
- 性能、数据规模、隐私和安全要求
- 是否允许联网、依赖第三方服务或使用特定许可证

如果缺少的信息会显著改变候选方案，先提出最少量的澄清问题；不影响初步调研的细节可以标记为待确认，不要阻塞整个调研。

### 2. 搜索 GitHub

使用明确的功能词、技术词和场景词组合检索 GitHub。优先查看：

- 项目主页和源码仓库
- README、文档、示例和架构说明
- LICENSE 文件
- Releases、提交活跃度和维护者信息
- Issues、Pull Requests 和已知限制
- 依赖清单、支持平台和部署方式

优先选择与需求直接相关、能访问到源码、许可证清楚且有可验证证据的项目。搜索结果页只用于发现候选，不作为最终结论的唯一来源。

### 3. 筛选候选项目

尽量找出 5 个最值得参考的项目，并剔除以下项目：

- 只解决表面相似问题，核心功能不匹配
- 没有可确认的源码或许可证
- 明显废弃、无法运行或与目标平台不兼容
- 存在与需求不相容的强制服务、闭源依赖或授权限制

候选不足 5 个时，明确说明“相关候选不足 5 个”，不要用低质量项目补足数量。

### 4. 比较候选项目

使用 Markdown 表格先给出横向比较，至少包含：

| 项目 | 解决的问题 | 匹配度 | 可直接使用 | 可二次开发 | 技术栈/实现思路 | 限制与风险 |
|---|---|---|---|---|---|---|

随后逐个展开说明：

1. 它具体解决了什么问题，哪些需求没有覆盖。
2. 与当前需求的匹配度：高、中、低，并给出理由。
3. 能否直接使用；若不能，最小改动是什么。
4. 技术栈、核心架构和关键实现路径。
5. 许可证、维护状态、平台兼容性、依赖、性能、安全和数据风险。
6. 最适合复用的模块，以及不建议直接复制的部分。

每个重要判断尽量附上项目链接、文件位置、版本、发布日期或其他可复核证据，并区分已确认事实与推断。

### 5. 给出三种方案

调研结论必须明确给出以下三个选项，并说明推荐理由：

#### A｜直接使用现成项目

适用于现有项目已覆盖主要需求，只需配置、部署或少量适配的情况。说明部署成本、未满足项和许可证要求。

#### B｜基于现有项目修改

适用于现有项目提供可靠基础，但需要增加功能、替换组件或适配环境的情况。说明要修改的模块、预计风险、维护成本和升级影响。

#### C｜确实不合适，再自己开发

只有当现有项目在功能、许可证、平台、维护性或安全性方面都不适合时才推荐。说明为什么不能复用，以及自研的最小可行范围和主要成本。

输出格式建议：

```markdown
## 结论

推荐：B｜基于现有项目修改

理由：...

## 需要用户确认

- A｜直接使用现成项目
- B｜基于现有项目修改
- C｜自己开发

请确认选项和需要调整的约束；确认前我不会开始写代码。
```

### 6. 等待确认

完成方案报告后停止，不自动进入编码、安装、克隆、部署或外部写入。只有用户明确选择 A、B 或 C，并确认必要的范围与约束后，才进入下一阶段。

## 成功标准

在交付调研结果前确认：

- 用户能看懂每个候选项目解决什么问题。
- 5 个候选（或不足 5 个的明确说明）都有匹配度和证据。
- 技术栈、实现思路、许可证和主要风险没有被遗漏。
- A/B/C 三种路径的成本和适用边界清楚。
- 推荐结论不是只按 Star 数量决定。
- 报告最后明确要求用户确认，并且尚未写代码。
